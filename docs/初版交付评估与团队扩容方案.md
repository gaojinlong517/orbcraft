# 初版交付评估与团队扩容方案

> 基线：`04c7b3f`（827 项自测全绿）。本文所有时间都是**基于当前代码量的判断**，不是实测；结论里的「人日」按每天 6 小时有效编码计。

## 1. 先给一个不乐观但准确的完成度

| 层 | 现状 | 完成度 |
|---|---|---|
| 规则层 `core` | 12 个包、7387 行、827 项自测、1124 条词条 | **可用** |
| 平台层 `common` / `fabric` | `fabric/src/main/java/com/orbcraft/fabric/` 是**空目录**，`build.gradle` 不存在 | **0%** |
| 美术层 | `carrier_models.json` 里 35 条映射，其中 11 条标记为 `NEW`（尚无模型） | **0%** |

`core` 里还有三个包**没有任何调用方**：`risk`（失控/混乱）、`rule`（自然语言时代的词表，已废弃）、`budget`（旧预算表，仅被旧的 `DraftSession` 用）。`hatch` 和 `render` 也只有自测在调。也就是说：**规则算得对，但游戏里还看不见它**。

真正的剩余工作量集中在「把纯 Java 逻辑接到 Minecraft 上」，这部分不能靠并行堆出来，见 §5 的关键路径分析。

## 2. 初版交付时间

三个里程碑，每个都对应一个**明确的验收动作**，而不是「感觉差不多了」。

| 里程碑 | 交付内容 | 验收动作 | 单人 | 6 智能体 |
|---|---|---|---|---|
| **M1 技术冒烟** | Gradle + Loom 工程、`/orb give` 直接发一个 Composition、球能投出、命中后召出**原版代理实体** | 进游戏输入一条命令 → 手里出现球 → 右键扔出 → 面前出现一个带名字、会打人的僵尸 | **5–6.5 人日** | **2–3 天** |
| **M2 内部可玩** | 四层构筑命令化、孵化读条、配额与定向卡接线、玩家存档、装备耐久、双人联机 | 两个客户端连同一服务端，各走完一次构筑，A 的球 B 扔不了 | **13–14 人日** | **7–8 天** |
| **M3 外观测试版** | BetterModel 接入、35 套模型、owo-lib 简易界面 | 玩家看到的是自己造的东西，而不是「一只叫火焰傀儡的僵尸」 | 代码 **8 人日** + 美术 **15–25 人日**（可并行） | **4–5 周** |

**M1 的 5–6.5 人日为什么不算多**：Loom 首次构建要拉 1GB 依赖、配置映射、跑通 `runServer`/`runClient` 双开，这一步在没做过的机器上一天很容易过去。剩下的才是写物品、投掷、生成三件事。

**M3 的瓶颈不是代码，是美术**：35 个载体里 18 个能复用原版资源、6 个只需重贴图、**11 个要从零建模**（枪、法杖、重锤、拳套、卷轴、符文、香炉、光灵、树人、图腾、巨蛇）。这 11 个是真实人力成本，加智能体帮不上忙。

> 如果你只想要「能上手玩一局」的版本：**M2 就是答案**，约 7–8 天（有智能体）或 2.5 周（单人）。M3 只影响「看起来像不像那个东西」。

## 3. 「可实际运行测试的版本」必须满足的条件

分成**必须**（缺一条就不算可测）和**可以欠着**（明确不算缺陷）。

### 必须满足

| # | 条件 | 怎么验证（不用问人） |
|---|---|---|
| 1 | 工程能起：`./gradlew runServer` 与 `runClient` 各起得来 | 两个进程都能到「Done」且客户端能进服 |
| 2 | 版本锁定写进 README：MC 1.21.11 / Java 21 / Fabric Loader / Fabric API 版本号 | 换台机器 clone 下来照 README 能构建成功 |
| 3 | 闭环可走通：**一条入口**开始构筑 → 四层选完 → 拿到球 | 命令返回值里能看到稀有度、孵化秒数 |
| 4 | 球能读条：背包物品有进度条，`lore` 显示百分比与剩余时间 | 拿出来看，进度条在动 |
| 5 | 球能投出并释放：右键 → 实体出现 → 有名字、有血量、能攻击 | 打它、被它打，数值与 Spec 对得上 |
| 6 | 状态持久：退出重进，在途孵化不丢、配额账本不重置、已有产物还在 | 停服 → 重启 → 三样都在 |
| 7 | 服务端权威：A 的球 B 扔不了；配额按人算 | 双客户端实测，日志里能看到拒绝原因 |
| 8 | 出错不崩服：配额满、球失效、参数非法都返回提示而不是异常堆栈 | 故意传错参数，服务端继续运行 |
| 9 | 可回归：`bash tools/verify-all.sh` 全绿 + 一份 30 分钟多人 smoke 清单 | 一条命令出结论 |

### 可以欠着（不算缺陷，但要在 README 写明）

- 没有图形界面，用命令 + 可点击文本代替
- 外观是原版实体代理，且**必须**向玩家提示「外观已降级」（`ModelCapability.shouldWarnPlayer()`）
- 建筑系统、袭城、新手村、PVP 模式 C 全部未实现（数据结构在，逻辑未接）
- 平衡性未调：900 局模拟只能证明「四档都有产出」，不能证明「好玩」
- `risk`（失控）、`rule`（词表）两个包先不接，前者等玩法确认，后者建议直接删

## 4. 哪些环节可以并行化

判断依据和上一轮相同：**文件所有权能否切干净**。平台层天然比 `core` 好切，因为它按「游戏对象」分家，而不是按算法分家。

| 流 | 内容 | 独占目录 | 依赖 | 现在能开工吗 |
|---|---|---|---|---|
| **S0** | Gradle + Loom + `fabric.mod.json` + 双 run 配置 | `build.gradle` `settings.gradle` `fabric/src/main/resources/` | 无 | **必须最先做，阻塞全部** |
| S1 | 球物品、投掷物、命中判定、耐久条 | `fabric/.../item/` `.../entity/orb/` | S0、S3 的生成接口 | S0 完成后 |
| S2 | 构筑交互（命令树 + 可点击文本 + 快照渲染） | `fabric/.../command/` `.../ui/` | S0 | S0 完成后 |
| S3 | Spec → MC 实体/属性映射、召唤物 AI 模式 | `fabric/.../spawn/` `.../mapping/` | S0 | S0 完成后 |
| S4 | 玩家存档（配额账本、在途票据、已有产物） | `fabric/.../store/` | S0、S3 的序列化约定 | S0 完成后 |
| S5 | 联机规则、事件优先级、按人配额、权限 | `fabric/.../server/` | S0 | S0 完成后 |
| S6 | 美术：11 个新建模型 + 6 个重贴图 + 资源包烘焙 | `client/` 与美术源文件 | 无（可与代码全程并行） | **现在就能开工** |
| **S7** | 联调、smoke 清单、版本锁、README | 主线 | S1–S5 | 末尾，不可并行 |

关键结论：**S0 和 S7 是串行咽喉，S1–S5 可以五路并行，S6 越早开始越好**。

## 5. 智能体编制：4 → 6

不建议超过 6。理由在 §6 的边际收益。

| 智能体 | 负责 | 主要交付 | 写入范围（硬边界） |
|---|---|---|---|
| `skeleton` | S0 工程骨架 | 能跑起来的最小空模组 + 双 run 脚本 + README 版本锁 | 根目录 Gradle 文件、`fabric/src/main/resources/` |
| `orb-item` | S1 球与投掷 | 物品、投掷实体、命中释放、耐久条渲染 | `fabric/.../item/`、`.../entity/orb/` |
| `build-ui` | S2 构筑交互 | 命令树、四层选择、快照 → 可点击文本 | `fabric/.../command/`、`.../ui/` |
| `spawner` | S3 生成与属性 | `Spec` → 实体/属性/装备映射，行为模式 | `fabric/.../spawn/`、`.../mapping/` |
| `persistence` | S4 存档 | Codec/NBT 序列化、登录恢复、离线封顶对接 | `fabric/.../store/` |
| `server-rules` | S5 联机与权限 | 事件注册、按人配额、A 球 B 扔的拒绝 | `fabric/.../server/` |

### 协作方式（比数量更重要）

1. **契约先行**。开工前由主线定 3 个接口：`OrbItemContract`（球 → 释放）、`SummonSpawner`（Spec → 实体）、`PlayerStore`（存档读写）。每个接口不超过 8 个方法，写进 `fabric` 的一个 `contract` 包里，六个人只读不改。
2. **包级所有权**。和上一轮一样，一个包同一时刻只有一个主人；跨包改动交给主线。
3. **worktree 隔离**。每个智能体一个分支一棵树，禁止 push / checkout / reset，禁止改别人的包。
4. **冻结窗口**。S0 完成前的所有平台层代码都只是草稿，不许合入 `main`。
5. **验收口径统一**。每个智能体必须贴出 `verify-all.sh` 的原始输出，不允许只写「全过」。

## 6. 预期收益与边际递减

上一轮实测数据可以作为参照：**4 个智能体 15 分钟完成 4 个模块**（人工顺序执行约 2–3 小时），合并零冲突，新增 613 项自测。

但要注意这 15 分钟只覆盖了「可并行的那部分」。对整体交付时间的影响是：

| 阶段 | 单人 | 6 智能体 | 缩短 |
|---|---|---|---|
| M1 | 5–6.5 人日 | 2–3 天 | **~55%** |
| M2 | 13–14 人日 | 7–8 天 | **~45%** |
| M3 | 代码 8 人日 + 美术 15–25 人日 | 4–5 周 | **~25%** |

降到 25% 的原因是 M3 的瓶颈在美术，不在代码。

**边际收益拐点**：4 → 6 大约还能再提升 20–25%；6 → 8 接近零，甚至为负。负收益来自两处：合并冲突概率随方数平方增长；每个智能体都要理解 `core` 的 7387 行与既有契约，上下文成本线性上升。

## 7. 额外开销与风险

| 风险 | 具体表现 | 缓解 |
|---|---|---|
| **契约漂移** | 上一轮 `Composition` 差点被改签名，导致并行引用它的模块编译断 | 契约冻结清单 + 只允许「加方法」不允许「改签名」 |
| **重复实现** | 上一轮 T1 与 T4 各自写了一遍「按族去重」 | 派单前先 grep 现有实现，写进任务书 |
| **验证幻觉** | 上一轮 `targetMissed` 分支被写成「已实现」，实际数据下不可达 | 要求贴原始输出；主线复核**断言本身**，不只看「通过」 |
| **合并冲突** | 六路并行时，`fabric.mod.json`、`entrypoint` 这类单点文件必冲突 | 这类文件归 `skeleton` 独占，其他人只读 |
| **验证时间通胀** | 827 项 + 平台层新测试，每轮全量跑越来越慢 | 分层：模块自测随改随跑，全量只在合入前跑一次 |
| **平台层不可预测** | Loom 版本、Fabric API 版本、BetterModel 适配都可能卡住 | S0 单独作为一次性冒烟目标，跑通再派其他人 |
| **美术硬瓶颈** | 11 个模型需要从零建模，agent 无法加速 | 第 1 天就启动，与代码完全解耦 |
| **上下文成本** | 每个智能体读 5500 行核心代码，慢且易错 | 给它「接口摘要 + 只读需要的那两个包」，不给全量 |
| **成本** | token 消耗随 agent 数线性增长 | 4 个够用的任务不要开到 6 个；S6 用人工美术更划算 |

## 8. 建议的下一步

1. **先做 S0**（`skeleton` 单干，不并行）：Loom 工程跑通 `runServer` + `runClient`，这一步不通，后面五路全白干。
2. **同时启动 S6 美术**：11 个模型的清单已经在 `carrier_models.json` 里，`asset: NEW` 的就是待建项。
3. S0 通了之后，一次性放出 `orb-item` / `build-ui` / `spawner` / `persistence` / `server-rules` 五路，主线只做接口与合并。
4. S7 联调前先写 smoke 清单（9 条验收条件就是清单本身），避免「跑起来了但没人知道该验什么」。
