# 构筑流程：四层确认制

> 实现：`core/src/main/java/com/orbcraft/core/build/`
> 自测：`core/src/test/java/com/orbcraft/core/build/BuildSelfTest.java`（150 项）
> 状态：已实现，已通过 900 局真实卡表模拟
> 变更：v3 把原「描述卡层」拆成**形态层**与**修饰层**，见 §9

---

## 1. 一句话定义

玩家先选**类型**，再抽**形态**、抽**修饰**、抽**效果**；每层都必须显式确认才进入下一层。
整个过程**不消耗任何可交易物** —— 没有点数、没有金币、没有重抽费用。

---

## 2. 状态机

```
                     ┌──────────────────┐
   new BuildSession  │  TYPE_CHOOSING   │  三选一，未选
                     └────────┬─────────┘
                       choose │  ▲ choose（再点一次 = 取消）
                              ▼  │
                     ┌──────────────────┐
                     │ TYPE_CONFIRMING  │  已选，等确认
                     └────────┬─────────┘
                    confirm()│  ← 唯一能推进的动作，同时发形态牌
                              ▼
                     ┌──────────────────┐
                     │  SHAPE_CHOOSING  │  5 张载体，未选
                     └────────┬─────────┘
                       choose │  ▲
                              ▼  │
                     ┌──────────────────┐
                     │ SHAPE_CONFIRMING │  已选 1 张，等确认
                     └────────┬─────────┘
                    confirm()│  ← 锁定形态，用它的 carrier_allow 过滤修饰池
                              ▼
                     ┌────────────────────┐
                     │ MODIFIER_CHOOSING  │  5 张元素/属性，未选
                     └─────────┬──────────┘
                       choose  │  ▲
                               ▼  │
                     ┌────────────────────┐
                     │MODIFIER_CONFIRMING │  已选，等确认
                     └─────────┬──────────┘
                    confirm()  │  ← 校验数量，同时发效果牌
                               ▼
                     ┌──────────────────┐
                     │ EFFECT_CHOOSING  │  5 张候选，未选
                     └────────┬─────────┘
                       choose │  ▲
                              ▼  │
                     ┌──────────────────┐
                     │EFFECT_CONFIRMING │  已选 1 张，等确认
                     └────────┬─────────┘
                    confirm()│  ← 返回 Composition
                              ▼
                       FINISHED
```

任何阶段都可以 `cancel()` → `CANCELLED`，不产生消耗。

### 为什么每层要拆成两个态

「选中即推进」的写法更短，但会丢两件东西：

1. **确认这个动作没有落点**。需求要求「未确认前不可推进」，如果选完自动走，确认就退化成动画。
2. **玩家没有改选余地**。手指点偏一次就得接受一张不想要的卡，而这套玩法一层只给 5 张。

所以 `choose()` 只登记意向，`confirm()` 是唯一的阶段跃迁入口 —— 代码里所有 `phase =` 赋新层的语句都写在 `confirm()` 里。

## 3. 可配置参数

`BuildConfig`，全部可在构造时替换，都有启动期校验。

| 参数 | 默认 | 允许范围 | 含义 |
|---|---|---|---|
| `shapeDealCount` | 5 | 3–9 | 形态层**候选**张数 |
| `SHAPE_PICK` | 1 | **常量，不可配** | 形态层**必选**张数（见 §3.2） |
| `modifierDealCount` | 5 | 3–9 | 修饰层候选张数 |
| `modifierPickCount` | 1 | 1–`modifierDealCount` | 修饰层必选张数 |
| `effectDealCount` | 5 | 3–9 | 效果层候选张数 |
| `effectPickCount` | 1 | 1–`effectDealCount` | 效果层必选张数 |
| `qualityWeights` | 白38/蓝32/金22/红8 | 非负，总和 > 0 | 品质抽取权重 |
| `shapeFloor` | 白 | 任意 `Tier` | 形态层保底品质（白 = 不保底） |
| `modifierFloor` | 白 | 任意 `Tier` | 修饰层保底品质 |
| `effectFloor` | 白 | 任意 `Tier` | 效果层保底品质 |
| `commonAvgMax` | 1.6 | > 0 | 平均点数 ≤ 此值 → 普通 |
| `rareAvgMax` | 2.8 | > 上者 | 平均点数 ≤ 此值 → 稀有 |
| `epicAvgMax` | 4.5 | > 上者 | 平均点数 ≤ 此值 → 史诗，超过即传说 |
| `extraCardHatchPct` | 0.15 | 0–2 | 每多带 1 张卡，孵化时长额外增加的比例 |

### 3.1 候选数与选取数为什么必须分开

需求里「共 5 张卡牌」说的是**候选**张数。如果把它和「玩家拿走几张」合成一个参数，
「5 张里挑 1 张」这种最基本的手感就锁死了，也做不了「困难模式发 3 张」。

### 3.2 为什么形态层只能选 1 张，而且不给开关

一件产物只有**一个形体**：一张外观 key、一套动画、一个碰撞箱。
允许选 2 张形态，`Composition` 就得回答「枪 + 法杖到底是哪个模型」——
这个问题在渲染层没有正确答案，所以不给配，只给常量 `BuildConfig.SHAPE_PICK = 1`。
要「一次造两件」是另一个需求（两件独立产物），不该靠放宽这里实现。

### 3.3 为什么修饰层默认选 1 张

选 1 张时玩家仍然在做真实取舍：5 张里只能留 1 个强化方向。
选 2 张会让组合张力更强，但需要重新校准稀有度分布 —— 留作待决项（§10）。

## 4. 抽取规则

### 4.1 候选池过滤（五道关）

按顺序过，任何一道不通过就剔除：

1. **类型匹配** —— `affix.base_type` 必须等于当前类型（`EQUIPMENT` / `SUMMON` / `CONSUMABLE`）或为 `ANY`
2. **族未用过** —— `usedFamilies` 里的族不再出现（同一件产物里同族只能有一次）
3. **载体允许** —— `carrier_allow` / `carrier_deny` 判定（选了枪就不该抽到「跳跃高度 +3」）
4. **元素允许** —— `element_allow` 空集表示不限
5. **族互斥** —— `excludes` 与已选族不能冲突

没有这几道，5 选 1 会频繁出现玩家读不懂的选项，而玩家读不懂时不会认为自己选错，只会认为系统坏了。

### 4.2 形态层：只发载体

```
载体池 = 该类型全部载体 → 洗牌 → 按族去重取 shapeDealCount 张 → 每张独立 roll 品质
```

形态层混入任何修饰卡都会破坏下一层的前提：修饰池要靠形态过滤，而形态层还没确认。

### 4.3 修饰层：形态确认后才生成

```
① carrier = 已确认形态的 carrier_id
② 修饰池 = 元素 ∪ 属性，用 ① 过滤（carrier_allow / carrier_deny / 元素限定 / 族互斥）
③ 洗牌 → 按族去重取 modifierDealCount 张
④ 每张独立 roll 品质
```

**这是拆层的全部理由。** 混层发牌时，修饰只能按「候选里那张载体」过滤；
如果形态可以换（甚至只是候选里有多个载体），玩家手里就会有一半修饰牌不适用于他最终选的形态。
拆层之后这个问题在结构上不存在 —— `dealModifier()` 只在 `commitShape()` 之后被调用。

元素卡与属性卡合在一层，是因为两者在玩法上是同一件事：「这件东西多了点什么」。
分开就得多一层确认，而玩家在 5 张里挑 1 张时，不会因为「这张是元素、那张是属性」而做出不同决策。

### 4.4 效果层

用**已确认**的载体与元素过滤效果池，再洗牌取张。此时形态与修饰的族都已进入 `usedFamilies`，
不会出现「修饰层选了火，效果层又给火焰强化」的重复感。

修饰选了属性卡时，元素为 `null`，效果池不按元素过滤 —— 这是设计，不是遗漏：
没有元素就没有元素亲和方向，硬套一个会让效果和产物对不上。

### 4.5 族去重：5 张必须是 5 个方向

元素特化族（`attr.elemResist` 之类）一个族在本载体上会展开成 9 条（9 个元素），
`family` 相同。直接取前 5 条，玩家可能看到
「火焰抗性 / 冰霜抗性 / 雷抗性 / 毒抗性 / 光抗性」—— 五张牌其实是同一个东西换了元素。

所以取牌时按 `family` 去重（`takeDistinct`）。实测最窄的载体也有 **19 个修饰族**，
去重后不会凑不满 5 张。

### 4.6 品质 roll

每张卡独立掷一次，**先掷后查**：

```java
Tier rolled = rng.pickTier(weights);   // 先掷
if (rolled.rank() < floor.rank()) rolled = floor;   // 再应用保底
TierData data = affix.tierData(rolled);             // 最后查表
```

绝对**不能**写成 `tiers.find(t -> t.points() <= budget)` 之类的回调 ——
那种写法每比较一次就重掷一次，红卡率会从 8% 悄悄掉到 2.6%（这个坑已经踩过一次）。

### 4.7 随机源

`SeedRandom`（mulberry32），与洗牌共用同一个实例。
**同一个 seed + 同一串选择 = 同一份结果**，玩家投诉时能拿 seed 重跑复现。

### 4.8 池子不足

发牌数取 `min(配置张数, 池子大小)`，不补齐、不重复。
如果池子连「最少要能选出 `pickCount` 张」都不满足，直接抛 `POOL_TOO_SMALL`，不静默降级。

类型层的可用性判定因此是**三层联合**的：形态够、**每个形态下最窄的修饰池**够、
效果够。只判一层会造出「选了装备，走完形态才发现修饰池是空的」这种死路。

## 5. 玩家交互顺序

| 步 | 玩家动作 | 系统响应 | 阶段变化 |
|---|---|---|---|
| 0 | 打开构筑 | 下发 `typeOptions()`（3 项，带可用性） | → `TYPE_CHOOSING` |
| 1 | 点「装备」 | 高亮该项，确认按钮可点 | → `TYPE_CONFIRMING` |
| 2 | 点「确认」 | **发 5 张形态牌** | → `SHAPE_CHOOSING` |
| 3 | 点第 3 张形态 | 高亮，计数 1/1，确认可点 | → `SHAPE_CONFIRMING` |
| 4 | 点第 1 张形态 | 超选被拒（形态只能 1 个） | `TOO_MANY_CHOICES` |
| 5 | 点「确认」 | 锁定形态 → **按它的 `carrier_allow` 刷新 5 张修饰牌** | → `MODIFIER_CHOOSING` |
| 6 | 点第 2 张修饰 | 计数 1/1，确认可点 | → `MODIFIER_CONFIRMING` |
| 7 | 点「确认」 | 校验数量 → **发 5 张效果牌** | → `EFFECT_CHOOSING` |
| 8 | 点第 4 张效果 | 计数 1/1，确认可点 | → `EFFECT_CONFIRMING` |
| 9 | 点「确认」 | 返回 `Composition` | → `FINISHED` |

关键点：

- **未选就点确认** → 抛 `NO_PENDING_CHOICE`，不是静默忽略。静默忽略会让 UI 表现成「点了没反应」，
  玩家会继续点，最后发出两三次请求。
- **超选** → 抛 `TOO_MANY_CHOICES`，不做「自动替换」。替换会让玩家以为自己选的还在。
- **再点同一张** → 取消选择，计数归零则该层回到 `*_CHOOSING`。
- **改选形态后**，修饰牌不会重发 —— 因为修饰牌还没生成。改选只影响「确认后按哪个载体过滤」，
  这是拆层带来的直接好处：不存在「换了形态但修饰牌还是旧的」这种中间态。

## 6. 最终输出结构

`Composition` —— 构筑与孵化/配额/落地之间唯一的契约。

| 字段 | 类型 | 说明 |
|---|---|---|
| `kind` | `BaseKind` | 装备 / 召唤物 / 消耗品 |
| `cards` | `List<DraftCard>` | 入选卡牌，顺序固定为 载体 → 元素 → 属性 → 效果 |
| `seed` | `long` | 随机种子，用于回放 |
| `rarity` | `Rarity` | 按平均品质算出的稀有度 |
| `totalPoints` | `int` | 品质点数总和（**仅展示，不参与任何扣减**） |
| `avgPoints` | `double` | 平均品质点数，稀有度的直接依据 |
| `hatchMultiplier` | `double` | 孵化时长倍率，1.0 = 不变 |

派生方法：

| 方法 | 返回 | 用途 |
|---|---|---|
| `carrierCard()` | `Optional<DraftCard>` | 载体卡（形态） |
| `carrierId()` | `Optional<String>` | 载体裸 id，外观匹配 |
| `modifiers()` | `List<DraftCard>` | 元素 + 属性 |
| `effects()` | `List<DraftCard>` | 效果 |
| `slots()` | `List<PickedSlot>` | 给 `settle` 包消费的形态 |
| `tags()` | `Set<String>` | 语义标签（火、剑、吸血…） |
| `hasUnrepairablePart()` | `boolean` | 是否带不可修复代价 |
| `brief()` | `String` | 一行播报 |
| `describe()` | `String` | 多行详情 |

默认配置下 `Composition` 恒为 **3 张 = 1 形态 + 1 修饰 + 1 效果**。
拆层没有改变产物结构，只改变了玩家「先定形体、再定强化」的顺序。

### 稀有度为什么用「平均点数」而不是「总点数」

选取张数可配。总和 14 在「选 2 张修饰」时是全红传说，在「选 4 张」时只是全金史诗 ——
总和不可比，均值才跨配置可比。

阈值与品质档的对应关系：

| 卡牌组合 | 平均点数 | 稀有度 |
|---|---|---|
| 全白 | 1.0 | 普通 |
| 全蓝 | 2.0 | 稀有 |
| 全金 | 4.0 | 史诗 |
| 一红两金 | 5.0 | 传说 |
| 全红 | 7.0 | 传说 |

`epicAvgMax` 定在 4.5 而非 5.0：5.0 时「一红两金」正好卡在边界掉回史诗，
传说只能靠「两红以上」产生，900 局实测仅 0.7% —— 玩家一个月见不到一次。4.5 之后约 2–4%。

### 孵化倍率

```
multiplier = 1.0
           + Σ(各卡 HATCH_TIME_PCT 代价)
           + extraCardHatchPct × (卡数 - 1)
```

第二项是「越强越久」在无点数系统后的唯一落点：卡越多，越强，也越久。
`Spec` 的构造器会对超出稀有度上限的秒数抛异常，所以最终仍由 `HatchTime.plan()` 截断。

## 7. 与旧 `DraftSession` 的关系

| | `draft.DraftSession`（旧） | `build.BuildSession`（新） |
|---|---|---|
| 层数 | 5 层（基调 + 载体/元素/属性/效果） | 4 层（类型 + 形态 + 修饰 + 效果） |
| 选择方式 | 每层发牌后 `pick` 即推进 | `choose` 登记 + `confirm` 推进 |
| 资源 | 28 点预算，选牌扣点 | 无任何资源 |
| 强度来源 | 玩家花点数买高品质 | 抽到什么就是什么 |
| 发牌入口 | `deal()` 是 public | 没有 public deal，只在 confirm 内发 |
| 重抽 | 花残损球重抽本层 | 无重抽 |

旧类**未删除、未修改**，162 项既有自测仍全过。两者共用 `AffixTable`、`DraftCard`、
`TierData`、`SeedRandom` 和 `settle` 层的词条映射规则。

新流程是玩法上的正式版本；旧版保留作为「带预算的对照实现」，等数值定稿后再决定去留。

## 8. 实测数据（900 局，真实 1124 条卡表）

```
稀有度分布：普通 186 (20.7%)  稀有 433 (48.1%)  史诗 259 (28.8%)  传说 22 (2.4%)
形态层发牌：5~5 张（均值 5.00）
修饰层发牌：5~5 张（均值 5.00）
效果层发牌：5~5 张（均值 5.00）
平均卡数：3.00
平均点数：7.26
孵化倍率：1.30 ~ 2.30
```

四档均有产出，无常量档位（旧流程在固定预算 28 下曾出现「传说 57%、普通 0%」的通胀）。

与拆层前（20.7 / 44.6 / 31.0 / 3.8）对比：稀有略升、史诗略降、传说略降，
差异落在抽样噪声范围内（每档样本 20–430 件）。拆层没有改变强度曲线 ——
它只改变玩家看到牌的顺序，不改变牌的池子与品质分布。

## 9. v3 变更：描述层为什么必须拆成两层

v2 的做法是「5 张里选 2 张，其中 1 张必是载体」。它有一个当时没暴露的隐含依赖：

> 那 4 张修饰牌，是按「候选里那张载体」过滤出来的。

载体位固定 1 张时它恰好不出问题。但这个设计把两件事绑死了：

1. **不能把载体位放开到 2 张**，否则玩家选了另一张，手里一半修饰牌不适用。
2. **不能给描述层加「换一批」**，因为换了载体，已发的修饰牌全部作废。

拆成「形态 5 选 1 → 刷新 → 修饰 5 选 1」之后，这两条约束都消失了：

| | v2（描述层选 2） | v3（形态 + 修饰） |
|---|---|---|
| 修饰牌何时生成 | 与形态同时 | 形态确认之后 |
| 修饰牌按谁过滤 | 候选里的载体 | **已确认**的载体 |
| 改选形态的影响 | 修饰牌可能作废 | 无影响（还没生成） |
| 载体位放开到 2 | 会出错 | 结构上仍然只允许 1（`SHAPE_PICK`） |

代价是多一次确认点击。收益是「读到的牌一定适用于你选的东西」——
在一个「5 张里只能留 1 张」的玩法里，这个保证比少点一次重要。

## 10. 待决事项

1. **形态层是否要给「换一批」**。当前没有 —— 一旦加上就必须回答「代价是什么」，
   否则等于把随机性变成无限刷新。如果要加，建议用「每日次数」而不是材料。
   拆层之后这一项更容易做了：重抽形态不会让任何已发的牌作废。
2. **修饰层是否允许选 2 张**。当前 `modifierPickCount = 1`。改成 2 会让「两个强化方向
   互相放大」的组合出现，但需要重新校准稀有度分布（阈值是按 1+1+1 三张卡定的）。
3. **元素是否要保底出现在修饰候选中**。当前 5 张修饰可能全是属性、没有一个元素，
   于是效果层不按元素过滤。若要「每次都有元素方向」，可以在 `takeDistinct` 里
   先各取 1 张元素再补属性 —— 但这会把元素的出现率从随机抬到 100%，属于数值改动，
   需要和稀有度曲线一起调。
