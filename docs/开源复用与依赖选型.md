# 开源复用与依赖选型

> 检索日期 2026-10-20 ｜ 目标：把「能直接用的」和「只能参考的」分开，避免重复造轮子，也避免踩许可证的坑
> 检索方式：GitHub 仓库实际克隆 + LICENSE 文件核对 + 发布元数据（Modrinth / CurseForge / Maven）

---

## 0. 结论先说

这次检索最大的收获不是「找到几个能抄的库」，而是**它推翻了我之前三个技术判断**，其中一个判断直接改变了整个项目的成本结构。

| 我之前的判断 | 实际情况 |
|---|---|
| 自定义实体外观必须自研渲染管线（隐形载体 + 手动同步 item_display） | **BetterModel 已经做完了**，MIT，服务端驱动，客户端零安装，还自带资源包生成 |
| AI 建模只能离线小时级，因为要体素化 + 重网格化 | **`.bbmodel` 本身就是 JSON**，AI 能直接产出，BetterModel 能直接吃 |
| 8~12 个骨架必须人工从零搭，是项目里唯一 AI 替不掉的环节 | 骨架可由 AI 生成初稿 + 人工微调，**不再是「从零搭骨骼层级」** |

净效果：**自定义实体这条最贵的链路，从「自研 6~8 周」降到「接一个 MIT 库 + 写适配层 1~2 周」**。

## 1. 许可证红线（先看这个，比功能更重要）

| 许可证 | 能不能抄代码 | 能不能当依赖 | 本项目涉及 |
|---|---|---|---|
| **MIT** | 可以，保留版权声明 | 可以 | BetterModel、owo-lib、Apotheosis、结构教程仓、多加载器模板 |
| **Apache-2.0** | 可以，保留声明 + NOTICE | 可以 | 未涉及 |
| **LGPL-3.0** | 不能抄进本体，**改了它就必须开源它** | 可以（动态依赖） | Polymer、MoogsStructureLib |
| **MPL-2.0** | 不能抄文件，改过的文件必须开源 | 可以 | Cobblemon、Charta |
| **无 LICENSE 文件** | **默认保留所有权利，不能抄** | 可以（仅调用 API） | **Flan** |

⚠ **Flan 是唯一一个风险项**：仓库根目录没有 LICENSE，`build.gradle` 里也没有 license 声明。这意味着法律上默认「保留所有权利」。可以把它当 mod 依赖调用它的公开 API，但**不能把它的代码搬进我们的仓库**，也不能假设它将来不会改许可。我们的 Zone 判定本来就该自己写（core 里已有），Flan 只做**可选桥接**。

## 2. 分层复用清单

### A 类：直接依赖，立刻省时间

| 组件 | 仓库 | 许可 | 替掉我们哪块 | 省下 |
|---|---|---|---|---|
| **BetterModel** | `toxicity188/BetterModel` | MIT | 自定义实体外观 / 动画 / 资源包生成 / 碰撞箱 | **4~6 周** |
| **owo-lib** | `wisp-forest/owo-lib` | MIT | 抽卡确认界面（声明式 UI）、配置界面、网络序列化 | 2~3 周 |
| **多加载器模板** | `pynickle/architectury-template` 等 | MIT | `common / fabric / neoforge` 三模块骨架 + AccessWidener 接线 | 1~2 周 |
| **Apotheosis 的 Affix 数据模型** | `Shadows-of-Fire/Apotheosis` | MIT | 词条表结构设计参考（**抄结构，不抄代码**，它是 NeoForge） | 设计时间 |

**BetterModel 为什么是最大的一笔**

它做的事和我们 §「双实体结构」那一章描述的一模一样，而且已经跑了两年：

```
BlockBench .bbmodel  →  服务端加载  →  自动生成资源包  →  下发客户端  →  item_display 组渲染
```

已确认的能力：
- cube / mesh / null object / locator 全支持，**没有「300 个 cube 上限」这个问题**
- 动画、Molang 表达式、IK 反向动力学
- 自定义碰撞箱（跟随骨骼旋转）
- 与基础实体同步（正好是「隐形载体 + 外观」的组合）
- 客户端**什么都不用装**（服务端推资源包）

接入坐标（Maven Central，已确认）：

```gradle
// 只引 API，不打包实现
compileOnly("io.github.toxicity188:bettermodel-mod-api:3.0.0")
```

> 注意：3.0.0 是 2026 年的大版本，**要求 Java 25**。1.21.11 对应的 2.2.0 版本走 Modrinth 坐标 `maven.modrinth:4h8rX3rt:GrvAMlui`，Java 21 即可。这是下面 §5 版本决策的核心。

**owo-lib 为什么选它而不是手写 Screen**

抽卡界面是我们每天点最多的 UI（5 张牌 + 品质色 + 点数 + 灰化态 + 重抽按钮）。手写 `Screen` 要处理布局、hover、动画、滚动、分辨率适配，而且每次改数值都要重排版。owo-ui 是声明式的：

```
卡牌行 = 水平布局，间距 6，子项 = 5 个 CardWidget（品质决定边框色，超预算时 greyed = true）
```

改一版 UI 是改几行声明，不是改几百行绘制代码。**这是纯赚的**。

## 3. 被推翻的三条旧结论（要改文档）

### 3.1 「AI 建模只能离线，小时级」

**错在假设了「AI 输出网格」。** BlockBench 的 `.bbmodel` 是**纯 JSON**：

```json
{ "elements": [ { "name": "head", "from": [4,4,4], "to": [12,12,12],
                  "faces": { "north": {"uv":[0,0,8,8], "texture":0} } } ],
  "outliner": [ { "name": "head", "origin":[8,8,8], "children":[] } ] }
```

这是坐标和拓扑，不是像素，**结构化的、可校验的、AI 完全能生成的格式**。生成一个 30~80 个 cube 的模型，token 量在几千以内，分钟级完成。

于是「AI 建模」从「离线小时级管线」变成「在线分钟级」，而「孵化读条 2~10 分钟」**正好把这个延迟藏起来了**。这是意外的好事：孵化时间不再只是幻术，它**真的在等模型生成**。

### 3.2 「8~12 个骨架必须人工从零搭」

仍然建议人工把关，但性质变了：AI 出初稿（骨骼层级 + 立方体布局 + UV 展开），人只做**审美调整**（比例、动画关键帧、贴图配色）。从「3~5 天从零搭」变成「每人半天微调」。

### 3.3 「服务端双实体结构要自研」

BetterModel 就是这个结构的成熟实现。**自研只在它不支持目标 MC 版本时才考虑**，且应保留 `ModelBackend` 接口以便切换。

## 4. 「合并进来」的实际动作

不是把别人的代码拷进仓库，而是在工程里确立四层依赖关系：

```
orbcraft/core            纯 Java，零 MC 依赖，已在（13 个类 + 450 词条数据）
      ↑
orbcraft/common          MC 逻辑层：Zone / 孵化 / 抽卡状态机 / 配额 / 袭城
      ↑
orbcraft/fabric          平台适配：事件、网络包、命令、渲染挂载
      ↑
外部依赖（只在此层出现）
     ├─ bettermodel-mod-api   （自定义实体外观）
     ├─ owo-lib               （抽卡 UI）
     └─ flan（可选，运行时探测）
```

具体三步：

**① 建多加载器骨架** —— 用 `pynickle/architectury-template` 做起点（MIT，已确认支持 AccessWidener 互通）。注意：**一期只做 fabric**，`neoforge` 目录留空壳，不要为了「将来可能支持」现在就把构建复杂度翻倍。

**② `ModelBackend` 契约已落地（不是草案，已编译并通过自测）**

```java
public interface ModelBackend {
    String backendId();
    ModelCapability capability();          // FULL / NAMED_VANILLA / NONE
    boolean available();
    ModelSpawnResult spawn(ModelRequest req); // 绝不抛异常
    boolean play(UUID host, String animation);
    void despawn(UUID host);
    int boundCount();
}
```

已落地的 7 个类（`orbcraft/core/src/main/java/com/orbcraft/core/render/`）：

| 类 | 职责 |
|---|---|
| `ModelBackend` | 唯一的可替换依赖抽象 |
| `ModelCapability` | 能力等级，决定**要不要向玩家提示外观降级** |
| `ModelRequest` | 宿主 UUID + modelId + 缩放 + 染色 |
| `ModelSpawnResult` | 三态（OK / DEGRADED / FAILED）+ 六种失败原因 |
| `ModelCatalog` | **预打包清单，运行时资源包变更的硬闸门** |
| `CatalogGuardBackend` | 校验层：拦未打包模型 + 吞掉第三方库异常 |
| `ModelBackends` | 按能力降序选择，失败一路退化到 `NullModelBackend` |

三个设计决定值得单独说明，它们都是「引了外部库之后才出现」的风险面：

**① `spawn` 不抛异常，必须返回结果。**
外观是附加层。一个模型文件缺失，不应该让玩家花 3 分钟孵化出来的恶龙召不出来。调用方拿到 `FAILED` 时继续走召唤流程，只是不挂外观。

**② `capability()` 存在的意义是「不骗玩家」。**
兜底后端能召出实体、能打、能掉血，但长得完全不是玩家造的东西。如果不把这个差别暴露到 UI，玩家的结论是「这游戏有 bug」，而不是「特效没加载」。

**③ `ModelCatalog` 是硬闸门，不是缓存。**
不在清单内的 modelId **直接拒绝，绝不降级去尝试生成**。理由见 §5.1：运行时生成模型 = 全服客户端同时卡 1~2 秒。

**BetterModel 不在场时退化为「原版实体 + 粒子 + 名称颜色」** —— 这是必须有的兜底，否则一个依赖缺失就让整个 mod 起不来。

> 自测结果：`core/src/test/java/.../RenderContractSelfTest.java`，**30 项全部通过**，覆盖依赖缺失、模型未打包、实现抛异常三种最坏情况。全部 `core` 类（21 个）已用 `javac --release 21` 编译通过，零警告。

**③ Flan 兼容层做成运行时探测**

```java
// 检测到 flan 才注册，不写在 fabric.mod.json 的 depends 里
if (FabricLoader.getInstance().isModLoaded("flan")) {
    FlanBridge.registerSafeZones(zones);
}
```

## 5. MC 版本定案（走 A 方案）

这是检索过程中冒出来的、之前完全没考虑的问题。**已定：A 方案。**

MC 生态在 2026 年完成了从「1.21.x」到「26.x」的版本号迁移，**很多库卡在中间**：

| 方案 | MC | Java | BetterModel | owo-lib | Flan | 生态整体 |
|---|---|---|---|---|---|---|
| **A. 1.21.11** | 1.21.11 | **21** | 2.2.0 ✅ | ✅ | ✅ 到 1.21.11 | 最完整 |
| **B. 26.2** | 26.2 | **25** | 3.x ✅ | ✅ | 移植中 | 迁移中 |
| C. 26.3（最新） | 26.3 | 25 | 3.2 ✅ | 部分 | 未跟上 | 前沿，风险高 |

**定案 A（1.21.11 + Java 21 + BetterModel 2.2.0）**，三条理由：

1. **Java 21 而不是 25**。Java 25 意味着所有玩家的启动器、你本机的 JDK、CI、Gradle 全要换。这跟玩法一点关系都没有，纯粹是运维成本。
2. **1.21.11 是 1.21 线的最后一个版本**，它的 bug 修完、mod 生态最完整、教程最多。
3. **迁移成本是线性的，不是指数**。等 26.x 生态稳定（预计 2~3 个季度）再升，那时我们的代码已经只有 `common` + `fabric` 两层，改的是适配层而不是核心逻辑。

> 代价：享受不到 26.x 的新渲染/新方块。但我们是「纯服务端 + item_display」方案，本来就不吃新渲染特性的红利。

### 5.1 ⚠ 修正：BetterModel 解决了什么，没解决什么

上一轮我说「AI 建模从小时级变成分钟级」，**这句话只对了一半，必须修正**：

| 事项 | 结论 |
|---|---|
| 自定义实体渲染 | ✅ 彻底解决（MIT / 服务端驱动 / 客户端零安装） |
| 模型格式 | ✅ `.bbmodel` 是纯 JSON，AI 可直接产出 |
| 动画 / IK / 碰撞箱 / 资源包生成 | ✅ 现成，不用自己写 |
| **新增模型要不要让客户端重载资源包** | ❌ **没有消失，只是被 BetterModel 接管了** |
| **AI 建模能不能"实时生效"** | ❌ **不能。生成变快了，生效没变快** |

机制是这样：BetterModel 通过**服务端资源包**下发模型文件。1.20.2+ 的客户端支持会话中热更新资源包，**不需要重连**，但每次更新都会让客户端卡 1~2 秒，而且是**全服同时卡**。

所以下面这条推论必须原样保留，不能因为引了库就放宽：

```
模型库在发版时一次性烘焙 → 运行时只允许用清单内的 modelId
AI 生成的新模型 → 进「待烘焙队列」 → 维护窗口统一打包
```

这也正是 `ModelCatalog`（见 §4 第 ② 条）被设计成**硬闸门**而不是缓存的原因：**它在物理上阻止了任何代码路径触发运行时资源包变更**。没有这道闸门，某处顺手传一个 AI 刚生成的名字，全世界玩家就会同时卡一下，而排查时看起来只是「服务器偶尔卡顿」。

**对玩法的直接影响**（这条决定了孵化读条到底是幻术还是真延迟，仍然需要分层）：

| 产物级别 | 外观来源 | 生效延迟 |
|---|---|---|
| 日常（普通～史诗） | 预打包骨架 + 程序染色（L1/L2） | 毫秒级，零重载 |
| 传说级专属外观 | AI 生成 → 异步烘焙 | 分钟级～下次上线 |

**结论没变，只是成本降了**：传说级仍然是「你今天造，明天才看到它长什么样」，但这件事从「要跑一套体素化管线」变成了「排进烘焙队列」。仪式感保留，工程风险大幅下降。

## 7. 决策记录（已定）

| 优先级 | 问题 | 定案 |
|---|---|---|
| **P0** | MC 版本选 1.21.11（Java 21）还是 26.2（Java 25）？ | **1.21.11 + Java 21 + BetterModel 2.2.0** |
| **P1** | 自定义实体外观：BetterModel 依赖，还是自研 item_display？ | **接受 BetterModel 作为依赖**（省 4~6 周），走 `ModelBackend` 接口，二期可换 |
| P2 | Flan 兼容层要不要做？ | 做，但只做「不冲突」这一件事，不做深度集成 |

**接受依赖时同时接受的三条约束**（写进工程规范，不是建议）：

1. **只依赖 `bettermodel-mod-api`，范围 `modCompileOnly`** —— 不 `include`，不打包进我们的 jar。玩家不装它也能进服，只是外观降级。
2. **不在 `fabric.mod.json` 的 `depends` 里声明它**，改放 `suggests`。否则它会从「可选增强」变成「硬前置」，与第 1 条矛盾。
3. **所有调用只能经过 `ModelBackend`** —— 业务代码里出现 `import kr.toxicity...` 视为违规。这样它弃坑时我们换实现的成本是「写一个类」，不是「改一遍项目」。

> 风险与对冲：BetterModel 是 MIT，作者弃坑我们接得走；但若它停在 1.21.11 而 MC 继续前进，我们会跟着卡住。这正是把接口抽出来的真正原因——**依赖本身可以换，接口不会**。

---

## 8. 一句话总结

**能找到的复用不是「少写点代码」，而是「少做一个自己没把握做对的东西」。**

自定义实体渲染这件事，我之前的方案是「自己搭一套隐形载体 + item_display 同步」，那是在 AI 建模还不可行的前提下才成立的。现在前提变了：BetterModel 已经把这条路走通两年、MIT、服务端驱动、客户端零安装，而且 `.bbmodel` 让 AI 建模从「小时级离线」变成「分钟级在线」。

**跟着变的是三件事：**
1. 自定义实体不再是项目最大的技术风险，降级成一次集
2. AI 建模从「不可行」变成「可行且快」，孵化读条顺便有了真实含义
3. 省下的 4~6 周应该投到**抽卡手感调到爽**和**袭城节奏**上——这两件事别人替不了，也最决定成败
