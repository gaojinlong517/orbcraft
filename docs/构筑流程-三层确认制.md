# 构筑流程：三层确认制

> 实现：`core/src/main/java/com/orbcraft/core/build/`
> 自测：`core/src/test/java/com/orbcraft/core/build/BuildSelfTest.java`（124 项）
> 状态：已实现，已通过 900 局真实卡表模拟

---

## 1. 一句话定义

玩家先选**类型**，再抽**描述卡**，最后抽**效果**；每层都必须显式确认才进入下一层。
整个过程**不消耗任何可交易物** —— 没有点数、没有金币、没有重抽费用。

---

## 2. 状态机

```
                     ┌──────────────────┐
   new BuildSession  │  TYPE_CHOOSING   │  三选一，未选
                     └────────┬─────────┘
                       choose │  ▲ choose（再点一次 = 取消）
                              ▼  │
                     ┌──────────────────┐
                     │ TYPE_CONFIRMING  │  已选，等确认
                     └────────┬─────────┘
                    confirm()│  ← 唯一能推进的动作，同时发描述牌
                              ▼
                     ┌──────────────────┐
                     │  DESC_CHOOSING   │  5 张候选，未选
                     └────────┬─────────┘
                       choose │  ▲
                              ▼  │
                     ┌──────────────────┐
                     │ DESC_CONFIRMING  │  已选 2 张，等确认
                     └────────┬─────────┘
                    confirm()│  ← 校验数量 + 载体数，同时发效果牌
                              ▼
                     ┌──────────────────┐
                     │ EFFECT_CHOOSING  │  5 张候选，未选
                     └────────┬─────────┘
                       choose │  ▲
                              ▼  │
                     ┌──────────────────┐
                     │EFFECT_CONFIRMING │  已选 1 张，等确认
                     └────────┬─────────┘
                    confirm()│  ← 返回 Composition
                              ▼
                       FINISHED
```

任何阶段都可以 `cancel()` → `CANCELLED`，不产生消耗。

### 为什么每层要拆成两个态

「选中即推进」的写法更短，但会丢两件东西：

1. **确认这个动作没有落点**。需求要求「未确认前不可推进」，如果选完自动走，确认就退化成动画。
2. **玩家没有改选余地**。手指点偏一次就得接受一张不想要的卡，而这套玩法一次只给 5 张。

所以 `choose()` 只登记意向，`confirm()` 是唯一的阶段跃迁入口 —— 代码里所有 `phase =` 赋新层的语句都写在 `confirm()` 里。

## 3. 可配置参数

`BuildConfig`，全部可在构造时替换，都有启动期校验。

| 参数 | 默认 | 允许范围 | 含义 |
|---|---|---|---|
| `descDealCount` | 5 | 3–9 | 描述层**候选**张数 |
| `descPickCount` | 2 | > `descCarrierSlots`，≤ `descDealCount` | 描述层**必选**张数 |
| `descCarrierSlots` | 1 | ≥ 1，< `descPickCount` | 候选里固定保留的载体张数 |
| `effectDealCount` | 5 | 3–9 | 效果层候选张数 |
| `effectPickCount` | 1 | 1–`effectDealCount` | 效果层必选张数 |
| `qualityWeights` | 白38/蓝32/金22/红8 | 非负，总和 > 0 | 品质抽取权重 |
| `descFloor` | 白 | 任意 `Tier` | 描述层保底品质（白 = 不保底） |
| `effectFloor` | 白 | 任意 `Tier` | 效果层保底品质 |
| `commonAvgMax` | 1.6 | > 0 | 平均点数 ≤ 此值 → 普通 |
| `rareAvgMax` | 2.8 | > 上者 | 平均点数 ≤ 此值 → 稀有 |
| `epicAvgMax` | 4.5 | > 上者 | 平均点数 ≤ 此值 → 史诗，超过即传说 |
| `extraCardHatchPct` | 0.15 | 0–2 | 每多带 1 张卡，孵化时长额外增加的比例 |

### 候选数与选取数为什么必须分开

需求里「共 5 张描述卡牌」说的是**候选**张数。如果把它和「玩家拿走几张」合成一个参数，
「5 张里挑 2 张」这种最基本的手感就锁死了，也做不了「困难模式发 3 张」。

### 为什么 `descPickCount` 必须大于 `descCarrierSlots`

等于的时候，2 个选取位里有 1 个被载体占死，玩家只剩 1 个位置可选修饰 ——
描述层的「取舍」退化成「再点一次确认」。校验在构造期就拦掉。

### 为什么是「选 2 张」而不是「选 1 张」

只选 1 张时，玩家只能在「一把枪」和「伤害 +3」之间二选一：
前者没有数值，后者没有形体，两种都无法单独成物。选 2 保证「形态 + 修饰」同时成立。

## 4. 抽取规则

### 4.1 候选池过滤（五道关）

按顺序过，任何一道不通过就剔除：

1. **类型匹配** —— `affix.base_type` 必须等于当前类型（`EQUIPMENT` / `SUMMON` / `CONSUMABLE`）或为 `ANY`
2. **族未用过** —— `usedFamilies` 里的族不再出现（同一件产物里同族只能有一次）
3. **载体允许** —— `carrier_allow` / `carrier_deny` 判定（选了枪就不该抽到「跳跃高度 +3」）
4. **元素允许** —— `element_allow` 空集表示不限
5. **族互斥** —— `excludes` 与已选族不能冲突

没有这几道，5 选 1 会频繁出现玩家读不懂的选项，而玩家读不懂时不会认为自己选错，只会认为系统坏了。

### 4.2 描述层的特殊顺序：先抽载体，再抽修饰

```
① 载体池 = 该类型全部载体 → 洗牌 → 取 descCarrierSlots 张
② 修饰池 = 元素 ∪ 属性，用第 ① 步选出的载体过滤 → 洗牌 → 取 descDealCount - descCarrierSlots 张
③ 合并后整体洗牌（位置打散）
④ 每张独立 roll 品质
```

**② 用 ① 的结果过滤**是必须的：修饰卡的 `carrier_allow` 是相对载体判断的，
同时抽会让「针对枪的属性」配上法杖，玩家看到的是 5 张互不相干的牌。

**③ 整体洗牌**是为了不让载体永远在第 1 格 —— 位置固定的话，玩家不用读卡就知道该点哪。

### 4.3 效果层

用**已确认**的载体与元素过滤效果池，再洗牌取张。此时描述层的族已进入 `usedFamilies`，
不会出现「描述层选了火，效果层又给火焰强化」的重复感。

### 4.4 品质 roll

每张卡独立掷一次，**先掷后查**：

```java
Tier rolled = rng.pickTier(weights);   // 先掷
if (rolled.rank() < floor.rank()) rolled = floor;   // 再应用保底
TierData data = affix.tierData(rolled);             // 最后查表
```

绝对**不能**写成 `tiers.find(t -> t.points() <= budget)` 之类的回调 ——
那种写法每比较一次就重掷一次，红卡率会从 8% 悄悄掉到 2.6%（这个坑已经踩过一次）。

### 4.5 随机源

`SeedRandom`（mulberry32），与洗牌共用同一个实例。
**同一个 seed + 同一串选择 = 同一份结果**，玩家投诉时能拿 seed 重跑复现。

### 4.6 池子不足

发牌数取 `min(配置张数, 池子大小)`，不补齐、不重复。
如果池子连「最少要能选出 `pickCount` 张」都不满足，直接抛 `POOL_TOO_SMALL`，不静默降级。

## 5. 玩家交互顺序

| 步 | 玩家动作 | 系统响应 | 阶段变化 |
|---|---|---|---|
| 0 | 打开构筑 | 下发 `typeOptions()`（3 项，带可用性） | → `TYPE_CHOOSING` |
| 1 | 点「装备」 | 高亮该项，确认按钮可点 | → `TYPE_CONFIRMING` |
| 2 | 点「确认」 | **发 5 张描述牌** | → `DESC_CHOOSING` |
| 3 | 点第 3 张 | 高亮，计数 1/2 | → `DESC_CONFIRMING` |
| 4 | 点第 1 张 | 同时选中，计数 2/2，确认可点 | → `DESC_CONFIRMING` |
| 5 | 再点第 1 张 | 取消该张，计数 1/2 | → `DESC_CONFIRMING` |
| 6 | 点第 5 张 | 计数 2/2 | → `DESC_CONFIRMING` |
| 7 | 点「确认」 | 校验数量与载体数 → **发 5 张效果牌** | → `EFFECT_CHOOSING` |
| 8 | 点第 2 张 | 计数 1/1 | → `EFFECT_CONFIRMING` |
| 9 | 点「确认」 | 返回 `Composition` | → `FINISHED` |

关键点：

- **未选就点确认** → 抛 `NO_PENDING_CHOICE`，不是静默忽略。静默忽略会让 UI 表现成「点了没反应」，
  玩家会继续点，最后发出两三次请求。
- **超选** → 抛 `TOO_MANY_CHOICES`，不做「自动替换最早一张」。替换会让玩家以为自己选的还在。
- **再点同一张** → 取消选择，计数归零则该层回到 `*_CHOOSING`。

## 6. 最终输出结构

`Composition` —— 构筑与孵化/配额/落地之间唯一的契约。

| 字段 | 类型 | 说明 |
|---|---|---|
| `kind` | `BaseKind` | 装备 / 召唤物 / 消耗品 |
| `cards` | `List<DraftCard>` | 入选卡牌，顺序固定为 载体 → 元素 → 属性 → 效果 |
| `seed` | `long` | 随机种子，用于回放 |
| `rarity` | `Rarity` | 按平均品质算出的稀有度 |
| `totalPoints` | `int` | 品质点数总和（**仅展示，不参与任何扣减**） |
| `avgPoints` | `double` | 平均品质点数，稀有度的直接依据 |
| `hatchMultiplier` | `double` | 孵化时长倍率，1.0 = 不变 |

派生方法：

| 方法 | 返回 | 用途 |
|---|---|---|
| `carrierCard()` | `Optional<DraftCard>` | 载体卡 |
| `carrierId()` | `Optional<String>` | 载体裸 id，外观匹配 |
| `modifiers()` | `List<DraftCard>` | 元素 + 属性 |
| `effects()` | `List<DraftCard>` | 效果 |
| `slots()` | `List<PickedSlot>` | 给 `settle` 包消费的形态 |
| `tags()` | `Set<String>` | 语义标签（火、剑、吸血…） |
| `hasUnrepairablePart()` | `boolean` | 是否带不可修复代价 |
| `brief()` | `String` | 一行播报 |
| `describe()` | `String` | 多行详情 |

### 稀有度为什么用「平均点数」而不是「总点数」

选取张数可配。总和 14 在「选 2 张」时是全红传说，在「选 4 张」时只是全金史诗 ——
总和不可比，均值才跨配置可比。

阈值与品质档的对应关系：

| 卡牌组合 | 平均点数 | 稀有度 |
|---|---|---|
| 全白 | 1.0 | 普通 |
| 全蓝 | 2.0 | 稀有 |
| 全金 | 4.0 | 史诗 |
| 一红两金 | 5.0 | 传说 |
| 全红 | 7.0 | 传说 |

`epicAvgMax` 定在 4.5 而非 5.0：5.0 时「一红两金」正好卡在边界掉回史诗，
传说只能靠「两红以上」产生，900 局实测仅 0.7% —— 玩家一个月见不到一次。4.5 之后约 4%。

### 孵化倍率

```
multiplier = 1.0
           + Σ(各卡 HATCH_TIME_PCT 代价)
           + extraCardHatchPct × (卡数 - 1)
```

第二项是「越强越久」在无点数系统后的唯一落点：卡越多，越强，也越久。
`Spec` 的构造器会对超出稀有度上限的秒数抛异常，所以最终仍由 `HatchTime.plan()` 截断。

## 7. 与旧 `DraftSession` 的关系

| | `draft.DraftSession`（旧） | `build.BuildSession`（新） |
|---|---|---|
| 层数 | 5 层（基调 + 载体/元素/属性/效果） | 3 层（类型 + 描述卡 + 效果） |
| 选择方式 | 每层发牌后 `pick` 即推进 | `choose` 登记 + `confirm` 推进 |
| 资源 | 28 点预算，选牌扣点 | 无任何资源 |
| 强度来源 | 玩家花点数买高品质 | 抽到什么就是什么 |
| 发牌入口 | `deal()` 是 public | 没有 public deal，只在 confirm 内发 |
| 重抽 | 花残损球重抽本层 | 无重抽 |

旧类**未删除、未修改**，162 项既有自测仍全过。两者共用 `AffixTable`、`DraftCard`、
`TierData`、`SeedRandom` 和 `settle` 层的词条映射规则。

新流程是玩法上的正式版本；旧版保留作为「带预算的对照实现」，等数值定稿后再决定去留。

## 8. 实测数据（900 局，真实 450 条卡表）

```
稀有度分布：普通 171 (19.0%)  稀有 408 (45.3%)  史诗 285 (31.7%)  传说 36 (4.0%)
描述层发牌：5~5 张（均值 5.00）
效果层发牌：5~5 张（均值 5.00）
平均卡数：3.00
平均点数：7.52
孵化倍率：1.30 ~ 2.30
```

四档均有产出，无常量档位（旧流程在固定预算 28 下曾出现「传说 57%、普通 0%」的通胀）。

## 9. 待决事项

1. **描述层是否要给「换一批」**。当前没有 —— 一旦加上就必须回答「代价是什么」，
   否则等于把随机性变成无限刷新。如果要加，建议用「每日次数」而不是材料。
2. **载体是否允许在描述层更换**。当前 `descCarrierSlots = 1`，玩家不能换。
   放开到 2 会带来 6 种外观 × 5 张牌的搜索空间，且修饰池的过滤规则要改成交集。
3. **效果层是否允许多选**。当前 `effectPickCount = 1`。改成 2 会让组合张力明显增强，
   但需要重新校准稀有度分布。
