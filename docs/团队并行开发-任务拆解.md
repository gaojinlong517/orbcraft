# 并行开发任务拆解（4 智能体）

> 基线提交 `e35e432`；集成目标 `main`。本文只描述「怎么切、谁负责、怎么合」，不重复各模块的设计文档。

## 1. 拆解思路：按**文件所有权**切，不按功能切

功能视角下这四个任务都叫「完善玩法」，很容易切出「A 做定向卡、B 也做定向卡接线」这种重叠。所以切割依据换成一个可机器校验的条件：

> **任意两个任务的文件集合交集必须为空。** 一个文件在同一时刻只有一个主人。

由此得到两条硬规则：

1. **新功能只能新增文件，不能借用别人包里的文件。** 定向卡的配额记在 `core/target/` 里，不去改 `quota/QuotaManager`；渲染层的载体映射新建 `CarrierModelRegistry`，不去改 `ModelCatalog`。
2. **跨包接线不分配给任何智能体，由集成阶段统一做。** 例如「把 `TargetPlan` 塞进 `BuildSession`」要动 `build/` 包，那就不能在 `build/` 已有主人（T4）时并行进行——这条被显式留成串行依赖。

第二条是这次拆解里最容易被忽略的地方：**并行度不是越高越好，边界处多一个并行任务，合并成本会指数上升**。四个任务里我只让一个（T4）碰 `build/`，就是为了让「接线」这一步只有一个人能改。

### 为什么是这四块

- **T1 / T2 是「内容侧的最后一公里」**：44 张定向卡与 35 个载体都已经在数据里，但都还没有代码去处——定向卡无法按类型发放，载体没有模型映射，等于数据资产闲置。
- **T3 是「链路断点」**：`Composition` 已经能结算成 `Spec`，`HatchSession` 能算进度，`QuotaManager` 能判配额，但**没有任何东西把它们按正确顺序串起来**，尤其「定稿才扣额度」这条规则目前无人实现。
- **T4 是「交互缺口」**：形态层没有「换一批」= 抽到不要的载体只能重开一局；修饰层选 2 张的能力目前是写死的单选取。

这四块彼此不共享文件，且都处于「有契约、缺实现」状态，是并行收益最高的一组。

## 3. 依赖图

```
            ┌──────── T1 定向卡分层配额 ────────┐
            │  (独立，仅读 target_cards.json)   │
            └───────────────┬──────────────────┘
                            │  接线：TargetPlan → BuildSession
            ┌──────── T4 构筑可选项 ───────────┐   （串行，集成阶段由主线完成）
            │  (独占 build/ 包)                 │◄──┘
            └───────────────┬──────────────────┘
                            │  Composition 不变
            ┌──────── T3 孵化链路 ─────────────┐
            │  (只调用 build/settle/quota)      │
            └──────────────────────────────────┘

            ┌──────── T2 载体渲染映射 ─────────┐
            │  (独立，仅读 affixes.carrier.json)│
            └──────────────────────────────────┘
```

**并行段**：T1 / T2 / T3 / T4 同时进行，无相互阻塞。
**串行段**：T1 的 `TargetPlan` 接进 `BuildSession` 必须等 T4 提交后做，否则两人同时改同一个文件。

T3 依赖 `Composition` 的**形状不变**。这是给 T4 的约束：可以加方法、可以加字段，但不得改变 `Composition` 现有构造签名——否则 T3 编译期就会断，而它当时看不到 T4 的改动。

## 4. 协同规则（每个智能体都必须遵守）

| 规则 | 原因 |
|---|---|
| 只在指定 worktree 内改文件，禁止 `cd` 到主工作树 `E:/gjl/orbcraft` | 四个 agent 同机同时跑，共享目录必然互相污染 |
| 禁止运行 `tools/gen-card-data.mjs` | 它会重写 1124 条数据文件，等于把所有人的数据基线改掉 |
| 禁止修改 `affixes.*.json`、`synergy.json`、`target_cards.json` | 数据是只读基线；要新数据就新建文件（T2 即如此） |
| 禁止 `git push` / `git checkout` / `git reset` / `git rebase` / `rm -rf` | 只允许在自己分支上 `git add` + `git commit` |
| 提交前必须跑完四个既有自测 | 基线：DraftSession 68 / Render 30 / Settle 64 / Build 150 |
| 统一编译口径 | `javac --release 21 -encoding UTF-8 -Xlint:all`，零警告才允许提交 |
| 报告必须含「发现的真实缺陷」一节 | 允许写「无」，但不允许省略——上一轮的 `.gitignore` 吞掉源码包就是这么发现的 |

## 5. 集成步骤（主线执行）

1. 依次合并 `feat/target-deck` → `feat/carrier-models` → `feat/hatch-pipeline` → `feat/build-options`（文件不相交，预期零冲突）。
2. **接线**：`BuildSession` 增加 `applyTargetPlan(TargetPlan)`，在 `dealShape` 前把指定载体固定进候选；配额扣减交给 T1 的 `TargetAllowance`，构建阶段本身不记账。
3. 全量回归：五套自测（含各任务新增）一次性跑通，编译零警告。
4. 单次集成提交 + 推送，保留四个特性分支作为工作留痕。
