## 1. 开工前每个人都要做的四件事

1. **单独 worktree + 分支**：`using-git-worktrees`，分支名 `s1-orb-item` 这类。
   禁止 `push`、`checkout`、`reset`，禁止改别人的包。
2. **先读两处再动手**：`fabric/src/main/java/com/orbcraft/fabric/contract/package-info.java`
   （责任边界）与本文第 4 节的「已有什么，别重写」。
3. **提交前跑** `bash tools/verify-all.sh`，**贴原始输出**，不接受「全过」三个字。
   注意第 4、5 步是契约冻结与 `fabric` 编译 —— 后者是唯一能发现「你改了契约却没改实现」的地方。
4. **失败用返回值，不要抛异常**。你的代码大多跑在事件回调与 tick 里，
   抛出去会打断整个 tick，症状是「服务器卡一下然后这条操作消失了」。

## 2. 通用约束（五条，全部来自上一轮的教训）

| 约束 | 为什么 |
|---|---|
| **契约只允许加方法** | 上一轮 `Composition` 差点改签名，三个模块同时编译中断。加方法前找主线，改完跑 `python tools/contract-freeze.py --write` |
| **一个包同一时刻只有一个主人** | 跨包改动交给主线合并，不要顺手改别人的文件 |
| **不要相信「应该能跑」** | 上一轮 `targetMissed` 分支被写成「已实现」，实际数据下不可达。每条分支都要能举出一个触发它的输入 |
| **异常只给参数错误** | 配额满、球没充满、查不到票据都是玩法分支，用 `HatchException` 的 `Code` 区分，不要 `RuntimeException` |
| **所有面向玩家的文字是中文短句** | 它们会直接进聊天栏，`NOT_READY` 这种码玩家读不懂 |

## 3. 各路线任务书

### S1 `orb-item` —— 球与投掷

**写入**：`fabric/src/main/java/com/orbcraft/fabric/item/`、`.../entity/orb/`

**实现**：`OrbItemContract`，并在初始化时 `Services.install(impl)`。
注意 `install` 对**不同实例**会抛异常（防两份实现），同一实例重复装是允许的（双端各初始化一次）。

**读这些就够**：

| 要什么 | 用什么 |
|---|---|
| 球上显示什么进度 | `HatchTicket.loreBar(nowTick)` / `progress(nowTick)` / `remainingSeconds(nowTick)` —— **不要自己画进度条字符串** |
| 投掷状态迁移 | `IncubationService.throwBall(ticketId, nowTick)`，它会把「条已满但状态还是 CHARGING」就地补迁移（玩家在两次 tick 扫描之间右键的情况） |
| 落地 | `IncubationService.deploy(ticketId, nowTick)`，**幂等**：实体命中和区块加载补偿都会调它，重复调用返回 `false` 而不是异常 |
| 造球 / 读球 | 契约自身；NBT 布局**必须**委托 `Services.playerStore().codec()`，不要另写一套 |
| 召唤 | `Services.summonSpawner().spawn(level, pos, spec, ownerKey)` |

**投掷物基类**：`net.minecraft.world.entity.projectile.throwableitemprojectile.ThrowableItemProjectile`
（1.21.11 存在，**在 `throwableitemprojectile` 子包里**，不是在 `projectile` 包下）。
父类是 `...projectile.ThrowableProjectile`。查这个方法时别用 `javap` 查 `projectile` 包的类名列表
来断定「不存在」——只列本包声明的类，子包里的看不到。

> 上一版这里写错过，记录一下免得再犯：当时按「声明的包」判断 1.21.11 没有这个类，
> 实际它在子包里。S1 按真实签名找到它，比照文档猜可靠。

**进度条**：物品显隐进度走数据组件（`net.minecraft.core.component.DataComponents` 已核实存在），
不要覆写旧的 `getBarWidth` / `isBarVisible` 那一套——1.21.5 起已经组件化了。

**验收（四条，都要能演示）**：
1. 球在背包里，进度条随 tick 增长，lore 显示百分比与剩余秒数。
2. 右键投出 → 实体飞出 → 命中点出现召唤物，名字与 `Spec.displayName` 一致。
3. 投掷时若还差 1 秒没满，提示是中文，不是异常栈。
4. 同一个球投出后再落地（重复触发），不会召出第二只。

**别做**：不要自己算稀有度、时长、配额（`core` 都算好了）；不要在球上囤一份 `Spec` 拷贝。

### S2 `build-ui` —— 构筑交互

**写入**：`fabric/src/main/java/com/orbcraft/fabric/command/`、`.../ui/`

**消费**：`BuildSession`（四层确认制）、`TargetDeck` / `TargetPlan` / `TargetAllowance`、
`IncubationService.preview/submit`、`Services.orbItem().createOrb(ticket)`。

**四层状态机的正确用法**：

```
phase()                 → TYPE_CHOOSING / SHAPE_CHOOSING / MODIFIER_CHOOSING / EFFECT_CHOOSING / FINISHED
typeOptions()           → 类型层有三个选项（装备 / 召唤物 / 消耗品）
chooseType(kind)        → 只能在 TYPE_CHOOSING 调
choose(int index)       → 其余三层用它（索引对应当前 cards()）
clearChoices()          → 取消本层已选（不是取消整局）
snapshot()              → 渲染用：requiredPickCount / canRerollShape / statusLine 都在里面
confirm()               → 推进一层；最后一层返回 Optional<Composition>
canConfirm() / confirmHint() → 按钮状态与「为什么不能确认」的中文提示
rerollShape() / shapeRerollsLeft() → 形态层重掷（有次数限制）
cancel()                → 放弃整局
```

**定向卡**：`TargetAllowance.use(...)` 返回**新实例**，必须把新实例存回你的会话；
忘记保存等于这次操作没发生（这是设计，不是 bug）。`TargetDeck.forKind(kind)` 取候选，
`BuildSession.applyTargetPlan(plan)` 把它接到发牌上。

**定稿后**：`HatchSubmit.of(ownerKey, composition, behavior, material)` →
先 `preview` 给玩家看（稀有度、时长、扣多少统御力、能不能造）→ 玩家确认才 `submit`。
**顺序不能颠倒**，`submit` 是整条链路上唯一扣配额的地方。

**验收**：
1. 一条命令走完四层，每层都能看到「还差几张」与「不能确认的原因」。
2. 点「确认」之前退出重进，配额没有被扣（`preview` 无副作用）。
3. 中途 `cancel()` 之后配额仍未被扣。
4. 造完之后手里出现球（用 `Services.orbItem().createOrb`，不要自己 `new ItemStack`）。

**别做**：不要自己算稀有度与孵化时长；不要把 `BuildSnapshot` 的字段重新拼一遍文案
（`statusLine()` 已经有了）。

### S3 `spawner` —— Spec → 实体

**写入**：`fabric/src/main/java/com/orbcraft/fabric/spawn/`、`.../mapping/`

**实现**：`SummonSpawner`，`Services.install(impl)`。

**属性映射（这一路唯一真正复杂的地方）**：

`Spec.attrs()` 的键由 `SpecSettler` 推导：
- 属性层：id `attr.<key>.<...>` → 键就是 `<key>`。当前数据里有 **96 个键盘**——
  `damage` / `armor` / `maxHealth` / `moveSpeed` / `lifesteal` / `critChance` / `critDamage` /
  `summonHealth` / `summonDamage` / `summonSpeed` / `elemDamage` / `elemResist` / `auraPower` /
  `splashRadius` / `statusChance` / `durability` / `stackLimit` / `charges` 等
- 效果层：id `effect.<family>.<...>` → 键是 `effect.<family>`（如 `effect.ignite`）
- 载体的 id 进 `tags`，元素 id 也进 `tags`

**映射表必须显式列出**，并且对未知键 `default` 分支打日志。不要写成
`attrs.getOrDefault(k, 0.0)` 然后静默忽略——96 个键里有几十个暂时不接是正常的，
但「哪些没接」必须能查，否则玩家会反馈「我堆了暴击但没伤害」而没人查得出原因。

**已知数据限制（记录，不要试图在 S3 修）**：`elemDamage` / `elemResist` 这类
<b>元素相关键在多元素时会合并成一个数</b>，键里不带元素维度。元素信息只在 `tags` 里。
所以「火系增伤 20%」落地时只能按 `tags` 里的元素给对应伤害，
不能指望从 attrs 里读出「火」这个维度。

**外观**：
- `CarrierModelRegistry` 取 `CarrierModelPlan`（`proxyEntity` / `modelId` / `animations` / `tintable`）
- `ModelBackends.select(catalog, candidates)` 选后端；`ModelBackend.capability()` 得到等级
- `capability().shouldWarnPlayer()` 为真时**必须**提示玩家「外观已降级」——不提示会被当成 bug

**归属**：`ownedBy(entityId, ownerKey)` 要跨重启有效，用
`net.minecraft.world.level.saveddata.SavedData`（已核实存在）落盘，别只放在内存 `Map` 里。

**验收**：
1. 给定一个 `Spec`，召出的实体属性符合 **`(代理基础值 + 绝对值加成) × (1 + 百分比加成/100)`**。
   `damage` / `maxHealth` / `armor` / `knockback` 是绝对值（desc 不带 `%`）；
   `summonHealth` / `summonDamage` / `moveSpeed` / `attackSpeed` / `critChance` / `critDamage`
   是百分比（desc 带 `%`）。**先加后乘**。
   上一版这里写成「血量 = maxHealth + summonHealth」，把两套单位混成一个加法，
   会得到僵尸 20+40=60 这种明显偏强的结果（本意是 20×1.4=28）。
2. `BehaviorMode.NONE`（装备/消耗品）传进来被拒绝，原因中文。
3. 同一个 `spec.id()` 连续 `spawn` 两次，只出一只。
4. 重启服务器后 `ownedBy` 仍然正确。
5. `NEW` 类载体（如 `treant`）走代理实体，且玩家收到降级提示。

**别做**：不要在 `SummonSpawner` 里再判断一遍模型能不能加载（`ModelBackend` 已有）。

### S4 `persistence` —— 存档

**写入**：`fabric/src/main/java/com/orbcraft/fabric/store/`

**实现**：`PlayerStore`（`load` / `save` / `codec()`）+ `OrbCodec`，`Services.install(impl)`。

**两个新入口是这路的关键**（`core` 刚补的，此前根本做不到）：

| 存 | 取 |
|---|---|
| `IncubationService` → `stateOf(owner)` / `ticketsOf(owner)` 组 `HatchSnapshot` | 登录时 `IncubationService.restore(HatchSnapshot)` |
| `TargetAllowance.snapshot()` | 登录时 `TargetAllowance.restore(perKind, retentionDays, snapshots)` |

**`restore` 的三个语义必须知道**（写错会静默改玩法）：
1. **只接在途票据**（`CHARGING` / `READY`）。`THROWN` 的球已经是世界里的实体，不该回到孵化栏。
2. **配额以存盘值为准**，不是从票据重算。原因是 `QuotaManager` 没有 release：
   已落地的产物仍占装备位，而它们不在票据列表里。只有存盘值低于在途票据所需时
   才会按票据修，并把 `quotaRepaired` 置真 —— 那个为真说明**存档写过一半**，要打日志。
3. **票据序号会按恢复的 id 自动推进**，这是 `restore` 内部做的，不要自己算。

**`ownerKey` 只有一个来源**：`PlayerStore.ownerKeyOf(uuid)`。任何地方自己拼字符串，
都会让同一玩家在两处拿到两套账本。

**保存时机**：退出 / 定时（建议 5 分钟）/ 关键状态变更后（submit、deploy、定向卡使用）。
**必须原子**：写临时文件再替换，或用 `SavedData` 一次性写整个 `CompoundTag`。
截断的存档会让 `restore` 走「按票据修配额」分支——那是兜底，不是常规路径。

**验收**：
1. 孵到一半停服，重启后球还在背包里、进度条**接着走**（不是从 0 开始）。
2. 装备位已满的玩家重启后仍然满（配额没被重置）。
3. 当天用过的定向卡额度重启后仍然被占用。
4. 新玩家首次登录不报错（`load` 返回 `PlayerState.fresh`，不是 `null`）。
5. 手动把存档文件截断一半，服务器能起来且日志里有 `quotaRepaired` 的告警。

### S5 `server-rules` —— 联机与权限

**写入**：`fabric/src/main/java/com/orbcraft/fabric/server/`

**负责**：

1. **唯一的 tick 推进点**。`IncubationService.tick(nowTick)` 全局只能有一处调用。
   两处都调会把「本次新就绪」的播报发两遍，玩家看到重复提示。
2. **按人配额**：`core` 已经按 `ownerKey` 隔离，S5 要保证传进去的 `ownerKey` 来自
   `PlayerStore.ownerKeyOf`，不是玩家名。
3. **A 的球 B 扔不了**：判定点在 `OrbItemContract.checkThrow(player, stack)`，
   S5 负责在投掷事件里**最早的位置**拦截并给出中文原因，不要在 S1 里判两次。
4. **权限**：管理类命令（直接发球、改配额）用权限等级，不要用「玩家名白名单」。
5. **服务端权威**：客户端发来的投掷请求只当「意图」，状态迁移一律在服务端做。

**验收**：
1. 双客户端，A 扔 B 的球被拒，日志里有原因。
2. 两人的配额互不影响（A 用满装备位，B 仍能造）。
3. 玩家掉线时在孵的球不复位、不重复播报。

**别做**：不要在事件里改 `IncubationService` 的内部状态——它所有方法都是 `synchronized`
且自带状态机，绕过去一定出「扣了没票」这类中间态。

## 8. 已知缺口与 S7 风险项

这一节是**合并时真实存在的未完成项**，不是待办清单的愿望。每条都写了「玩家会看到什么」，
因为验收时最容易漏掉的正是「代码在、编译过、但玩家那边什么都没发生」。

### 8.1 球在空中时重启，落地会漏召或双召（需发版前修）
`IncubationService.restore` 只接 `CHARGING` / `READY`，`THROWN` 不在其中 ——
这是**有意的**：THROWN 的球已经是世界里的实体，恢复进孵化栏会让「同时孵化」计数虚高。
代价是重启后这张票在服务里查不到，落地时 `deploy` 走 `UNKNOWN_TICKET`，
S1 的兜底按球物品自带票据兑现一次。

- 玩家看到什么：球飞出去，落地**可能什么都没有**，或者极少数情况下出两只
- 失败窗口：球在空中的 1–2 秒遇上 `stop`
- 正解：`core` 增加一个「只登记、不占栏」的 THROWN 恢复入口（`restore` 加 `includeThrown`）
- 为什么这轮不修：要动 `core`，而 887 项自测是全项目底座，五路合并当口动它风险大于收益
- 联调手测：投出后立刻 `stop`，再 `start`，确认落地**恰好一次**

### 8.2 critChance / critDamage / lifesteal 没有接线（最容易被误判为「已实现」）
`SummonAttrMap` 把这几个键**接进来了**，但 1.21 没有「暴击率/暴击伤害/吸血」属性，
它们只能靠伤害事件（`ServerLivingEntityEvents.AFTER_DAMAGE` 一类）自己掷骰与结算。
S3 本轮没写那个事件。

- 玩家看到什么：堆了 30% 暴击的召唤物，伤害数字一次都不变 —— 且**没有任何报错**
- 当前处理：不静默 —— 日志把它们列进「未落地的键」清单
- 修法：一个伤害回调 + 对 `lifesteal` 的治疗，约 100 行，独立于本轮的映射表

### 8.3 元素维度在 attrs 里丢失
`attr.elemDamage.fire.bow` 经 `SpecSettler` 取第二段后变成 `elemDamage`，多元素合并成一个数。
元素信息只在 `tags` 里。所以「火系增伤 20%」落地只能按 tags 给整体加成，
**做不到火/雷分开算**。这是数据模型限制，不在 S3 修。

### 8.4 三种产物均已落地（2026-10-21 补齐消耗品）
**装备（2026-10-21 补）**：新增 `fabric/equip/EquipmentDeployer`，球落地后产出一件
带属性修饰符的原版物品，投掷者在线进背包（满则掉脚下），不在线掉在落点。

- 载体 → 原版物品的映射表在 `EquipmentDeployer.BASES`，12 个装备载体全覆盖。
  其中 `gun` / `staff` / `dagger` / `gauntlet` 原版没有对应物，用最近替代品并在 lore 里
  如实写「外观为占位」——四个载体的玩家会看到不是自己想象中的形状，这是既定占位。
- 属性：`damage` / `maxHealth` / `armor` / `armorToughness` / `knockback` / `reach` 走加法，
  `moveSpeed` / `attackSpeed` 走乘法（value/100）。与召唤物同一套单位口径。
- `critChance` / `critDamage` / `lifesteal` 仍然不落地（原版没有对应属性），
  只记 debug 日志，原因同 8.2。

**消耗品**（v1 已落地，口径待策划确认）：`consume` 包，投出后在落点半径 4 格结算一次效果，
按 attrs 结算 —— `damage` 打非主人、`maxHealth` 治疗主人（÷4）、`moveSpeed` 给非主人 5 秒缓慢。
这三个除数是工程侧的第一次落地，不是策划结论；换数值只改三个常量。

**测试注意**：装备球投出后不会留下实体，物品直接进背包（或掉在落点）。
如果投出去什么都没发生，先看聊天栏/动作栏有没有「落地失败：…」，
再看日志里有没有「装备落地遇到未知载体」。

### 8.5 召唤物外观资产缺失
- 载体模型：24/35 已烘焙，其余 11 个走代理 + 降级提示
- **球物品本身没有任何 assets**（`assets/orbcraft/items/orb.json` 不存在），
  游戏内是紫黑方块。S6 出图前这是预期状态
- 当前 `capability()` 恒为 `NAMED_VANILLA`：仓库里没有任何 BetterModel 适配器，
  于是**每只召唤物都会提示一次「外观已降级」**。适配器就位前这属于噪声，
  真机上会被当成 bug 上报 —— 要么尽快补适配器，要么改成「每个玩家只提示一次」

### 8.6 召唤物归属（2026-10-21 已补「不打主人」）
- **不打主人**：`combat/CombatInit` 在 `END_SERVER_TICK` 里清掉「目标是主人」的目标。
  只遍历账本记录的实体（`SummonLedger.entityIds()`），不扫全世界 Mob。

### 8.8 一个操作层面的坑（值得写进 README）
`tools/fast-compile.sh` 的类路径文件 `/tmp/orbcraft-cp.txt` 里含**主 worktree 的**
`.gradle/loom-cache` 绝对路径。主 worktree 的 `build/` 或 `.gradle/` 被清掉之后，
五个 worktree 会一起编译失败，报「找不到 net/minecraft/...」。重跑一次
`./gradlew -q printCompileClasspath | tail -1 > /tmp/orbcraft-cp.txt` 即可。

## 9. 图形界面与开发期命令

### 9.1 构筑界面（卡牌点选）
`/orb build` 之后服务端会额外推一份 `BuildScreenS2C`（JSON 字符串），客户端收到后
打开 `BuildScreenGui`：把这一屏的所有按钮铺成可点的卡片。

- **状态只有一份**：界面不复制任何规则，点按钮就是发一条原版命令（`orb card 2`）。
  命令仍然可用；界面挂了玩法不受影响。
- **按钮从聊天渲染里「顺手登记」**：`BuildScreens.button()` 在生成可点击文本的同时
  记下 `{标签, 命令, 色调}`，所以界面和聊天不会出现两套文案。
- **已知限制**：界面只显示按钮，不显示每个选项的词条数与详细说明（那些在聊天里，
  按 `F` 打开聊天还能看到）。要做成「带图标和描述的卡片」需要客户端自己渲染物品图标，
  属下一轮。

### 9.2 菜单里的「跳过孵化」按钮（仅开发环境）
构筑界面底部会多一个 `⚡ 跳过孵化（仅开发）` 卡片，点一下等价于 `/orbdev hatch`，
点完界面立刻刷新。它用 `FabricLoader.isDevelopmentEnvironment()` 判断，
正式构建里自动不出现 —— 不依赖「记得上线前删掉」。

### 9.3 `/orbdev`（开发期命令，上线前必须处理）
| 子命令 | 作用 |
|---|---|
| `/orbdev hatch` | 把自己所有在孵的球直接推进到「就绪」，跳过等待 |
| `/orbdev tickets` | 列出自己的票据、状态、剩余秒数 |

实现方式是**推进时钟**而不是改 `startTick`：`IncubationService.tick(now + 24h)` 只把
「已到点但仍 CHARGING」的票翻成 READY，不写入任何只存在于开发期的状态。

⚠️ **它没有权限门槛**（离线开发服里玩家不是 op，加了门槛等于永远用不了）。
发布前必须改成 `AdminPermissions.requirement()`，或把 `OrbDevCommand` 从发布包里删掉。

### 9.4 一个会直接崩客户端的坑：实体渲染器
注册了 `EntityType` 却没注册客户端渲染器，表现**不是「看不见实体」，是整个世界渲染循环 NPE**：

```
java.lang.NullPointerException: Cannot invoke "EntityRenderer.shouldRender(...)"
because "entityRenderer" is null
  at EntityRenderDispatcher.shouldRender
  at LevelRenderer.extractVisibleEntities
```

只要那个实体一旦出现在视野里（例如球被投出去），客户端立即崩溃，且崩在渲染线程，
堆栈里看不到任何模组类名——很难指向「少注册了一行」。

修法：`EntityRenderers.register(OrbEntities.PROJECTILE, ctx -> new ThrownItemRenderer<>(ctx))`。
**新增任何自定义实体，客户端渲染器必须和 EntityType 同时注册。**
