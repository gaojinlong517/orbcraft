# 美术派单 · S6

> 依据 `core/src/main/resources/data/carrier_models.json`（35 条载体映射）。
> 待开工 **17 项**：11 个 `NEW`（从零建模）+ 6 个 `REPLACE`（重贴图 / 微调网格）。
> 另 18 项 `REUSE` 直接复用原版资源，**不需要美术投入**，列在文末仅供核对。

## 0. 一句话结论

**先把 6 个 `REPLACE` 做完，就能在游戏里第一次看到「玩家造的东西长得像它自己」** ——
这 6 项是改原版模型，单项 0.5–1 天，不需要骨骼动画。11 个 `NEW` 里真正吃时间的是
3 个生物（精灵 / 树人 / 巨蛇），它们要完整骨骼 + 死亡动画，其余 8 个是单个物体。

## 1. 交付物格式与命名（不按这个命名会白做）

每个载体交三样东西：

| 项 | 格式 | 命名 | 说明 |
|---|---|---|---|
| 源文件 | BlockBench `.bbmodel` | `<carrier_id>.bbmodel` | 保留可编辑性，后续改动画不用重做 |
| 导出 | BetterModel `.json` + `geo` 结构 | `model.<carrier_id>.json` | **`model.` 前缀由代码拼出，文件名必须一致** |
| 贴图 | PNG RGBA，2 的幂 | `<carrier_id>.png` | 规格见下表 |

`<carrier_id>` 取本文表格第一列（如 `staff`、`treant`），不是中文名。

## 2. 代码会校验的硬约束（不符合会在启动期直接报错）

`CarrierModelPlan` 的构造器是**严格校验**的，以下四条满足不了，整个模组起不来：

1. `modelId` 必须**等于** `model.` + `carrierId`。写成 `model.staff_v2` 会被拒。
2. 动画名只能是 `idle` / `walk` / `attack` / `death` / `special` 五个之一。
   自造 `cast`、`swing`、`charge` 这类名字不会报错但**永远不播** —— 那等于静默失效，
   比报错更难查。
3. 没有动画的模型（符文、图腾），代码要求 `note` 字段里写明「静态」，否则会被当成漏配。
4. 代理实体必须在原版白名单内（写错实体 id 不会编译报错，只会召唤失败）。

另外两条**美术侧**的硬约束，代码查不出来但会毁掉效果：

5. **`tintable=true` 的载体，贴图必须是灰度遮罩**。染色是乘算的，贴图本身带颜色时
   最终颜色 = 贴图色 × 元素色，比如蓝色贴图染火元素会变成灰紫色。
   需要固有色（木头、金属）的情况，把固有色画进**不会被染的通道**或单独一块 UV。
6. **1 格 = 16 像素**是原版基准。手持模型按 16 px/格建，进游戏后靠 `scalePct` 统一缩放；
   反过来先做成 256 px 一格再缩，贴图会糊成一片。

## 3. 规格基线

| 类别 | 包围盒 | 面数上限 | 贴图 | 说明 |
|---|---|---|---|---|
| 手持装备（`item_display`） | 最长边 0.6–2.0 格 | 2,500 tris | 128×128 | 第一人称握持，宽度别超过 0.3 格 |
| 消耗品（`item_display`） | 0.3–0.8 格 | 1,500 tris | 128×128 | 要有明确的「正面」，投出后会旋转 |
| 静态立件（`rune` / `totem`） | 高 0.5 / 2.0 格 | 1,000 tris | 128×128（+64×64 自发光） | 不需要骨骼 |
| 生物（`allay` / `warden` / `ender_dragon` 骨架） | 高 1.0 / 3.0 / 4.0 格 | 8,000 tris | 256×256 | 必须有多段骨骼，见各行动画要求 |

动画帧数基线（20 tick = 1 秒）：

| 动画 | 帧数 | 循环 | 说明 |
|---|---|---|---|
| `idle` | 60t | 是 | 呼吸 / 悬浮 / 微风，幅度小 |
| `walk` | 32t | 是 | 仅生物用 |
| `attack` | 12t | 否 | 前摇 4t / 命中 1t / 收招 7t，**命中帧必须在第 5 帧**（伤害判定卡这一帧） |
| `special` | 30t | 否 | 施法 / 抛投 / 后坐，可以有位移 |
| `death` | 24t | 否 | 只播一次，末帧必须落地或彻底消失 |

## 6. 交付后必须做的一步（否则模型不会生效）

代码里 `CarrierModelPlan.baked()` 的规则是 **`asset != NEW`**，
`CarrierModelRegistry.toCatalog()` 只登记 `baked()` 为真的模型。

也就是说：**模型做完了但 `carrier_models.json` 里还写着 `NEW`，它依然不会被加载**，
玩家看到的还是原版代理实体。每交付一项，需要把该条记录的 `"asset": "NEW"` 改成
`"asset": "REPLACE"`，然后跑一次 `bash tools/verify-all.sh`。

这不是可以省的手工步骤 —— 反过来，如果为了「先让它能显示」把所有 `NEW` 提前改成
`REPLACE`，资源缺失就会被伪装成「已就绪」，玩家看到的是空白而不是有解释的降级。

## 7. 验收标准

每项交付按这三条验，缺一条都算没完成：

1. **形状**：把模型摆在展示台上，正面 / 侧面 / 背面各看一眼，与原版代理实体的体积感相差不超过一档
   （不能出现「巨蛇比龙还大」这种尺度错乱）。
2. **动画**：`attack` 的命中帧在第 5 帧；`death` 末帧落地；循环动画首尾帧能接上（无跳变）。
3. **染色**：`tintable=true` 的模型，用火（`#FF6B3D`）与冰（`#7FD3FF`）各染一次，
   两次结果必须是同形不同色，且固有色区域不被染。

## 8. 不需要动工的 18 项（核对用）

苹果、护甲、斧、兽、猎鹰、弓、弩、晶簇、龙、傀儡、蘑菇、药水、种子、盾、虫群、剑、骸骨、光灵。

这些在原版里已有合适的模型与贴图，`asset` 为 `REUSE`，首版直接用代理实体 + 染色即可。
其中 `wisp`（光灵）与 `spirit`（精灵）用的是同一个代理基座 `allay`，但两者定位不同：
光灵是复用（只染色），精灵要新建（半透明 + 无腿）。别把它们合并成一项。
